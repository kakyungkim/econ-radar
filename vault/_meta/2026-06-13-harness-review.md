## 발견된 문제와 처방 (우선순위순)

### ① 품질 게이트가 문체에만 있고 사실에는 없다 — 최대 리스크
- 자동 발행 전환으로 사람 게이트가 빠졌는데, 남은 검수(style-critic)는 가장 덜 위험한 실패(어색한 문장)만 막음. 잘못된 수치·환각 출처는 그대로 블로그·텔레그램으로 나감.
- improvement-log가 이미 반복 기록: 오라클 capex IR 미확인, 요격률 미검증 단일 소스, 비오미아 단일 소스 3회 이월.
- **처방(2026-06-13 적용)**: `fact-checker` 에이전트 신설, 파이프라인 T4.7(style-critic 다음, render 앞). 핵심 수치 최대 10개 원문 대조, 출처 없는 수치 차단, 단일 소스 표기, 1차 출처 승격.

### ② 3층(저술)이 비어 있다 — 시스템 존재 이유 미작동
- reports/blog/book 전부 빈 채 4호 발행. "누적이 리포트→블로그→책으로 자란다"는 전제에 forcing function이 없었음.
- **처방(2026-06-13 적용)**: 주간 trend-synthesizer 클라우드 루틴 신설(`trig_01T6E6z5nnuxspGqov3PGJ9K`, 일요일 21:00 KST). `vault/reports/YYYY-Www-동향.md` 자동 생성 → 텔레그램 알림. 외부 발행은 안 함(사람 판단).

### ③ 로컬/클라우드 이중 운영의 균열
- vault 핵심 디렉터리(raw/analysis/daily/topics)가 gitignore라 클라우드 런이 자기 역사를 못 봄 → 큐레이션이 로컬 수동 전용으로 남고, 멀티위크 연속성(딜 추적) 불가.
- **처방(2026-06-13 적용)**: 레포 private 전환 후 vault 전체 git 추적. 클라우드 루틴이 큐레이션(T6)까지 수행하도록 데일리 루틴 프롬프트 갱신.

### ④ 비용 구조 — 가장 비싼 단계가 가장 판단이 필요 없는 단계
- 1회 발행 ≈ 43만 토큰 중 report-renderer가 9.3만(최대). 151KB HTML을 매일 LLM이 처음부터 생성 → 토큰 낭비 + 양식 드리프트(d96cc4a 수정 커밋이 그 증거).
- **처방(2026-06-13 적용)**: `scripts/render_html.py` + 템플릿으로 결정적 렌더 전환. md 구조 계약은 `scripts/NEWSLETTER-FORMAT.md`. report-renderer 역할은 "계약 점검 + 스크립트 실행 + 검증"으로 축소.

### ⑤ MOC가 append-only 로그화 (미적용 — 다음 후보)
- topics/*.md에 매일 날짜 블록 추가 → 3개월이면 파일당 ~90블록. 읽기 비용 선형 증가, "지식 그래프"가 아니라 날짜순 더미가 됨. 투자테마/투자전략, 유망기업/신약개발전략 중복 드리프트도 미해결.
- 처방안: 각 MOC 상단에 큐레이터가 매일 **갱신**하는 "현재 상태 요약"(핵심 흐름 5줄), 타임라인은 아카이브로. "추가"가 아니라 "갱신"이 있어야 지식이 압축된다.
